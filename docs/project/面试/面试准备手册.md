# 智效工坊 - 面试高频问题与参考答案

> 本文包含目标型参考答案。性能与效果数字必须替换为当前 CI/评测制品中的实测值；无证据时应明确回答“尚未实测”。

> 范围：覆盖架构 / AI / 后端 / 工程 / 创新点 / MetaGPT 模式
> 每题均提供参考答案 + 追问方向 + 应答思路

---

## Q1. 为什么选择多 Agent 架构而不是单 Agent？

**参考答案**：
本项目任务具有「多步骤多角色」特征（拆解 / 检索 / 生成 / 审核），单 Agent 难以同时高质量完成：
1. **职责分离**：4 Agent 各有 system prompt，专注能力边界、可单独优化；单一 Agent 的 prompt 容易膨胀，风格漂移。
2. **可控条件分支**：LangGraph 状态机可显式定义"审核不过 → 返工"，业务规则可解释；单 Agent 只能依赖隐式 prompt。
3. **可观测 + 可中断**：每个节点是独立 Agent，可在任意节点切中断、恢复、补日志，便于链路回溯。
4. **可演进**：新增 / 替换 Manager 只需新增一个节点 + 改一条边；单 Agent 改 prompt 容易回归。

**追问方向**：多 Agent 通信成本高？怎么权衡 token 成本？
**应答思路**：通信通过 Environment 共享上下文 + Redis 队列，避免完整对话重传；token 成本通过专精 prompt + 缩短字段（不影响输出质量）覆盖。

## Q2. LangGraph 工作流编排的核心设计是什么？

**参考答案**：
1. **GraphState**：全局 TypedDict 承载 subtasks / materials / drafts / review_round / status / error
2. **节点 + 边**：decompose → retrieve → generate → review；review 通过 `add_conditional_edges` 判断 `pass_`，最大 REVIEW_MAX_ROUNDS=2
3. **checkpoint**：每节点结束向 Redis `task:cp:{id}` 写 graph_state，可断点续跑
4. **控制流**：节点入口检查 `task:run:{id}:control=stop`，优雅 END（status=paused）
5. **事件可观测**：节点末尾向 Redis `sse:event:{id}` 推送事件，前后端双向

本期通过自实现 WorkflowEngine 薄封装与 LangGraph 思想保持同构，业务层只依赖 `AbstractExecutionEngine` 接口；后续迁移到 langgraph 包，业务零改动。

**追问**：为什么不直接 import langgraph？
**应答**：langgraph 0.0 系列仍在快速迭代，破坏性升级风险高。我们通过薄封装保证业务层稳定；待 0.1 GA 后平滑替换。

## Q3. 知识沉淀系统是如何保证质量的？

**参考答案**：
1. **触发门槛**：仅 succeeded 任务自动沉淀，failed 仅抽"踩坑"
2. **抽取规则**：LLM 必输出 JSON 含 type/title/content/tags/categor；长度 <50 字 / 含隐私 / 无引用计数的直接丢弃
3. **去重**：MD5 哈希去重；语义 cosine ≥0.92 视重复，保留质量分高者
4. **质量分机制**：初始 0.5；usage_count 增长 + 用户点赞上分；<0.3 默认不进入召回
5. **时间衰减**：90 天线性衰减，避免陈旧经验长期占位
6. **A/B 评估**：沉淀前可走 quality_reviewer 二次审核

**追问**：质量分冷启动阶段没有用户反馈怎么办？
**应答**：依赖 usage_count + reviewer.risk 反向加权；冷启动期对未引用素材自动降分。

## Q4. 如何解决 Agent 之间的状态同步问题？

**参考答案**：
1. **状态唯一权威**：GraphState 是唯一全局状态，不允许 Agent 直接 mutation 另一 Agent 的私有 memory
2. **通信只走 Environment**：Agent 间通过消息发布订阅，按 watch 列表过滤
3. **业务运行态派生**：Redis `task:run:{id}` 只读副本，由 GraphState 派生（HSET 每节点末尾）
4. **checkpointer 原子写**：HSETNX 防止覆盖；resume 加载最近 checkpoint 重建状态
5. **SSE 通道旁路**：所有事件只追加到 Redis 队列，不参与状态流转（去耦）

**追问**：并发 10 任务会不会冲突？
**应答**：每个 task_id 隔离一个 GraphState 实例，所有 Redis key 含 task_id 前缀，无共享状态。

## Q5. SSE 流式推送的技术难点是什么？

**参考答案**：
1. **Nginx 默认 buffering**：会缓冲到一定量才发出，导致前端 token 延迟。解决：`proxy_buffering off` + 响应头 `X-Accel-Buffering: no`
2. **超时切断**：默认 `proxy_read_timeout 60s` 不足以承载长任务。解决：SSE 块单独配置 `proxy_read_timeout 0` + `proxy_send_timeout 0`
3. **浏览器 EventSource 限制**：不支持 Authorization Header。改用 `fetch + ReadableStream` 解析 SSE 帧
4. **断线再续**：服务端发心跳 5s；客户端取消时清理 `sse:client:*` Redis key；任务断线保存进度 → 重新订阅即恢复
5. **背压控制**：服务端 `blpop` 超时 5s 自动让出协程；任务结束后端发送 `task_end` 自动闭环

**追问**：为什么不用 WebSocket？
**应答**：单向推送场景下 SSE 更轻，HTTP 兼容、自动重连；任务控制指令可通过 REST POST 实现，双向需求不强。

## Q6. 系统的并发能力如何？做了哪些优化？

**参考答案**：
- 当前仓库实现异步接口、队列和资源限制；P50/P95、QPS 与并发任务上限尚需在目标部署环境实测
- 关键优化：
  1. FastAPI 全异步 + SQLAlchemy 2.0 async 连接池（pool 10 + 20 overflow）
  2. Redis 限流 + 幂等 + 任务队列入队即返回，长任务背后跑
  3. LangGraph 节点边检查 `control` 标志位；超长任务 30min 强制 END
  4. Chroma/Milvus 检索参数可调；CI 覆盖 1 万级功能基准，百万级延迟尚待手工基准
  5. 前端 chunk 分包（element-plus / markdown / vendor），路由懒加载
  6. Nginx gzip + 静态资源 30 天缓存

**追问**：怎么测并发？
**应答**：wrk 接口压测 + Locust 端到端模拟用户 + docker stats 监控资源。

## Q7. 这个项目最大的技术挑战是什么？如何解决的？

**参考答案**：多 Agent 与 SSE 流协同 + 知识质量保障两件事联动：
- Agent 输出 token 必须实时贴到前端；又要被 quality_reviewer 检查；又要写入 drafts 状态、最后还要沉淀知识
- 我做了三件事：
  1. **状态统一**：所有要写的内容统一存 GraphState 给后续节点用
  2. **流式 + 落库并行**：Streaming 走 Redis `sse:event:*` 队列+状态写 Redis HSET，两条管道并行
  3. **沉淀异步**：任务成功事件触发 `_watch_done` 后台任务做知识抽取 + 向量化，不阻塞用户主链路

**追问**：如果沉淀失败怎么办？
**应答**：失败仅写 SSE error 事件并落到 `knowledge_items.status=vector_pending`；补偿服务每 5min 重试，不影响主任务结果交付。

## Q8. 如果重新设计这个系统，你会做哪些改进？

**参考答案**：
1. **直接用 LangGraph 官方 Postgres checkpointer** 替代自研 Redis checkpointer，省自实现成本
2. **向量库默认 HNSW** 早期就内置，不依赖 Chroma 默认配置
3. **意图分类用本地 BERT 微调模型** 替代每次 LLM 调用，可省 50ms
4. **沉淀流程走消息队列 (Kafka/RabbitMQ)** 而非内置 asyncio task，承受更大并发
5. **引入 OpenTelemetry** 替代自定义 trace_id，与 Grafana/Prometheus 一体化
6. **前端用 Vite + Vitest 单测 + Playwright E2E**，本期测试未覆盖前端

**追问**：为什么没一开始就这样做？
**应答**：项目周期 3 周，需要在"够用 + 可演进"与"工程完美"中权衡；以薄封装保护业务层可演进，给后期 Litmus 留路径。

## Q9. MetaGPT 的 Role-Team-Environment 架构模式是如何应用到项目中的？

**参考答案**：
1. **Role（角色）**：`BaseRole/BaseAgent` 暴露 `_think/_act/_observe` 生命周期；4 个 Agent 即 4 个具体 Role（TaskDecomposer=ProductManager 等）
2. **Team（团队）**：`Team.hire/disband/run` 在业务层管理多 Role；engine 层用 `WorkflowEngine` 做编排
3. **Environment（环境）**：消息发布/订阅总线；按 watch 决定哪个 Agent 接收谁的消息
4. **Memory（记忆）**：每个 Agent 私有 working memory；系统级 long-term 走 Chroma
5. **Plan/Task（计划）**：拓扑排序 + dependent_task_ids + current_task；GOAL-02 单测覆盖循环依赖抛错
6. **Tool（工具）**：ToolRegistry + `@register_tool` + ToolRecommender；GOAL-06 落地
7. **Skill（技能）**：SkillManager 加载 config.json + skprompt.txt；GOAL-07 落地

**关键点**：本项目不直接 import MetaGPT 框架包，而是按其思想自实现轻量版，保持解耦可演进。

**追问**：如果 MetaGPT 发版升级要不要跟进？
**应答**：以"模式同构"为原则，不绑定具体实现；我们的轻量实现可兼容其模式，无需硬升级。

## Q10. 如何设计一个可扩展的 Agent 系统？Tool Registry 是如何工作的？

**参考答案**：
1. **抽象基类**：`BaseTool` 子类提供 async `run`，可被 LangGraph 节点直接调用；`@register_tool` 工程级，自描述可被 LLM function-calling
2. **统一注册表**：`ToolRegistry` 全局单例；按名 / 按标签两维索引
3. **自动 Schema 生成**：装饰器扫描类 docstring + ast.parse + type hints → 生成 OpenAI function-call 兼容 schema
4. **工具推荐**：`ToolRecommender._score` 按 1.0 满分三路加权（name 0.3 / description perKeyword 0.1 / tag 0.2），返回 top-K
5. **运行时挂载**：意图识别后从工作流 DSL 解析 `agent.tools`，推荐 + 用户自定义组合挂到 Agent 实例
6. **新增工具**：仅写一个 `@register_tool(tags=["..."])` 类即可被全系统识别；零侵入
7. **安全控制**：Terminal / Editor 类工具按空间 RBAC 开关；默认禁用危险工具

**追问**：你们怎么防 LLM 误用工具？
**应答**：1) 仅在 system prompt 中暴露可用工具白名单；2) 工具参数 ast 校验 + 限流；3) Terminal 类日志全记入 tool_invocations 表便于事后追溯。

## 通用应答思路

回顾项目时使用 STAR 模型：
- **S**ituation：行业知识沉淀难、复杂任务执行效率低
- **T**ask：3 周交付"执行即沉淀"AI 工作台
- **A**ction：MetaGPT 模式落地 + LangGraph 思想 + SSE + RAG 三路融合 + Docker 一键
- **R**esult**：展示当前 CI、测试、Diff 和评测制品；在真实评测未完成时明确说明目标值尚未达成验证

度量自驱：量化指标必须能定位到固定评测结果或 CI 制品；没有证据时只讨论目标，不宣称达成。
