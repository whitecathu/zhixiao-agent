# 智效工坊 - 面试高频问题与参考答案

> 本文包含目标型参考答案。性能与效果数字必须替换为当前 CI/评测制品中的实测值；无证据时应明确回答“尚未实测”。

> 范围：覆盖架构 / Agent 运行时 / 后端 / 工程 / 扩展模型
> 每题均提供参考答案 + 追问方向 + 应答思路

---

## Q1. 为什么交付形态不是 4 个独立 Agent？

**参考答案**：
已交付产品是一个**安全的软件工程 Agent harness**，不是内容平台上的 4 个独立 Agent。默认运行时是**一个模型 + 类型化工具 + PluginHost + 权限/审批 + 验证门禁**：
1. **默认图是单循环**：LangGraph `StateGraph` 节点是 `intake → discover → plan → execute → verify → finalize`（外加审批等待、worktree 准备、失败修复）。这是同一套工具循环的阶段，不是四个进程/四个模型实例。
2. **`routing.py` 里的 planner/explorer 是事件标签**：`run_started` 会带上 `agents: ["planner", "explorer", …]`，用来标注任务类型对应的角色名，**不是**独立 Agent 进程。
3. **多角色只作为可选切片**：Workflow DSL 可按角色动态建图；Worker 在 `engine=metagpt` 时走 MetaGPT Team 垂直切片。这两条都不是默认故事，也不该写成「已上线的 4-Agent 产品」。
4. **真正要证明的是可控性**：workspace 边界、`CommandPolicy` 拦截 `git push` / `rm -rf`、未信任目录不加载 `.zhixiao/plugins`、写任务必须有验证结论或带理由的 waiver。多 Agent 通信并不是本仓库的主矛盾。

**追问方向**：那为什么代码里还有 `agents` 字段和 MetaGPT？
**应答思路**：字段是路由/可观测标签；MetaGPT 与 Workflow DSL 是可选引擎，默认 CLI/Worker 走单 Agent 工具循环。面试时主动划清「默认产品」和「实验切片」。

## Q2. LangGraph 工作流编排的核心设计是什么？

**参考答案**：
1. **`AgentState`**：TypedDict 承载 `run_id` / `permission` / `plan` / `events` / `verification` / `termination_reason` / `usage` 等；节点只返回新 state，不另搞一套业务图引擎。
2. **默认节点**：`intake → discover → plan →（可选 awaiting 计划审批）→ prepare_workspace → execute 工具循环 → verify →（失败则 repair）→ finalize`。条件边决定审批、继续调用工具、修复或结束。
3. **checkpoint**：`AsyncSqliteSaver`（`langgraph-checkpoint-sqlite`）。`thread_id` 就是 `run_id`。进程重启后可用同一 run_id `resume`。图状态**不**写 Redis。
4. **计划审批**：需要审批时节点走 LangGraph `interrupt({kind:"plan", ...})`，控制面/CLI 再 `Command(resume={"approved": ...})`。
5. **协同中断**：`zhixiao interrupt` 写入 `{state_dir}/control/{run_id}`；runtime 读到后 **unlink**，再 `interrupt({"kind":"operator_stop"})`。先删文件是为了 resume 不会立刻再停。同一 `run_id` 可恢复工具循环，不只是改清单状态。

仓库已经直接依赖正式 `langgraph` 包，没有「自研 WorkflowEngine 以后再迁 LangGraph」，也没有 Redis `task:cp:{id}` 图 checkpointer。

**追问**：为什么不用 Redis 做图 checkpoint？
**应答**：平台 Redis 负责队列和 SSE（Streams）。图要和 LangGraph 的 interrupt/resume 对齐，SQLite checkpointer 是当前实现；多机共享 checkpoint 若要做，才是后续存储选型，不是「已经有一份 Redis graph checkpointer」。

## Q3. 知识沉淀系统是如何保证质量的？

**参考答案**：
知识检索是可选切片（`knowledge_search` 工具、向量/图谱抽象存在），**不是默认编码闭环的质量门禁**。质量分、语义去重阈值、90 天衰减、百万级召回等产品指标**尚未上线、尚未实测**；CPU 单测和内存适配器不能外推召回率。写任务的质量门禁是验证结论（测试/waiver），不是知识库分数。

**追问**：那简历上能不能写 RAG 完成率？
**应答**：不能。没有固定评测制品就回答「尚未实测」。

## Q4. 如何解决运行状态同步？图 checkpoint 在哪里？

**参考答案**：
1. **图状态唯一权威**：LangGraph `AgentState` + SQLite `AsyncSqliteSaver`。resume 用同一 `thread_id=run_id` 从 checkpoint 恢复，不是从 Redis 重建图。
2. **平台运行态走 Redis Streams**：Worker 消费 `run:queue`，事件写 `run:events:{id}`，API SSE 按 cursor / `Last-Event-ID` 续读。这是传输层，不是 graph checkpointer。
3. **MySQL** 持久化 TaskRun、步骤、审批、制品等控制面记录。
4. **不要说** `task:cp:{id}` / Redis HSETNX 是 LangGraph checkpointer——那是旧设计，当前代码没有这条路径。

**追问**：并发多个 run 会不会抢 checkpoint？
**应答**：每个 run 一个 `thread_id`；本地 CLI 的 SQLite 文件按运行时配置；平台侧任务按 `run_id` 隔离 Redis Stream。没有共享的「4 Agent 私有 memory 互改」。

## Q5. SSE 流式推送的技术难点是什么？

**参考答案**：
1. **Nginx buffering**：会攒包再发给浏览器。解决：`proxy_buffering off` + 响应头 `X-Accel-Buffering: no`（仓库 `infra/nginx/nginx.conf` 与 API SSE 头一致）。
2. **超时切断**：SSE 长连接单独加大或关闭 `proxy_read_timeout`；普通 API 仍保持短超时。
3. **浏览器 EventSource 限制**：不支持 Authorization Header。改用 `fetch + ReadableStream` 解析 SSE 帧。
4. **断线再续**：服务端心跳；客户端用 `Last-Event-ID` 或 `cursor` 从 Redis Stream 续读；去重后不会把已消费事件再当新步骤执行。
5. **背压**：`xread` 阻塞超时后让出协程；任务终态由 Worker 写入结果流，前端以结构化 `RunResult` 为准。

**追问**：为什么不用 WebSocket？
**应答**：单向推送场景下 SSE 更轻，HTTP 兼容、自动重连；暂停/恢复/审批走 REST，双向需求不强。

## Q6. 系统的并发能力如何？做了哪些优化？

**参考答案**：
- 当前仓库实现异步接口、队列和资源限制；P50/P95、QPS 与并发任务上限**尚未实测**，不要报数字。
- 关键点（与实现一致）：
  1. FastAPI 异步 + SQLAlchemy 2.0 async 连接池。
  2. Redis 限流/幂等 + Streams 入队即返回，长任务在 Worker 跑。
  3. **中断不是「LangGraph 读 Redis control」**。本地 CLI：控制文件 → runtime unlink → `interrupt(operator_stop)`，同一 run_id 可 resume。平台 Worker：轮询 Redis `run:control:{run_id}=stop` 后 **cancel asyncio 任务**。两条路径都要说清楚，不要混成图引擎读 Redis 标志位。
  4. 向量/图谱/LoRA 最多是 CPU stub；百万级召回与 GPU 训练**未上线、未实测**。
  5. 前端分包与路由懒加载；Web 有 Vitest，不声称「前端零测试」。
  6. Nginx gzip + 静态缓存；SSE 关闭 buffering。

**追问**：怎么测并发？
**应答**：先给目标环境的压测方案（接口 wrk、端到端 Locust、docker stats），测完再报；现在没有制品就说尚未实测。

## Q7. 这个项目最大的技术挑战是什么？如何解决的？

**参考答案**：把「能改仓库的 Agent」做成**可中断、可恢复、不可越权、验证结论不可编造**，而不是把 4 个角色 prompt 串起来：
1. **协同中断要对齐 LangGraph**：只改 Session 清单不够；必须 `interrupt(operator_stop)` 停在工具循环，resume 才能继续同一 `run_id`。行为门禁 `tests/evals/run_behavioral.py` 的 `interrupt-resume` 用 ScriptedModel 覆盖这条。
2. **权限与命令策略在工具执行前拦截**：`git push` / `rm -rf` 无审批不得进 subprocess；`ask` 模式即使权限是 `edit` 也只暴露只读工具。
3. **验证缺失显示「未回报」**：Web 运行证据条不把空 verification 渲染成「已通过」。

**追问**：知识沉淀失败怎么办？
**应答**：知识切片失败不应冒充写任务成功。写任务终态只看 verification / waiver / 结构化失败原因。

## Q8. 如果重新设计这个系统，你会做哪些改进？

**参考答案**：
1. **图 checkpoint 已经是 LangGraph SQLite**，不要再提「用官方 checkpointer 替换 Redis graph checkpointer」——那份 Redis checkpointer 不存在。若改进，是评估 Postgres checkpointer 做多 Worker 共享，或把平台 Worker 的 Redis cancel 也收成同一套 `operator_stop` interrupt，便于远程 resume 与本地语义一致。
2. 向量库与 GPU LoRA 仍是实验切片；上线前要有独立基准，不能用 CPU stub 外推。
3. 意图/任务分类若要省 token，需离线评测后再替换 LLM 调用，当前没有延迟数字。
4. 平台事件已用 Redis Streams；更大扇出再考虑独立消息总线，不是从零替换图状态。
5. 可观测性可继续接到 OpenTelemetry，与现有 Prometheus/Grafana 对齐。
6. **前端测试已存在**：Vitest（含运行证据条）；Playwright 是 CI 容器里的 **UI 烟测**，不证明真实编码 Agent 完成了跨栈任务。

**追问**：为什么没一开始就做多机 Postgres checkpoint？
**应答**：先保证单进程 interrupt/resume 与权限门禁正确；共享 checkpoint 是部署形态问题，不是「补一个不存在的 Redis checkpointer」。

## Q9. MetaGPT 的 Role-Team-Environment 怎么用在本项目里？

**参考答案**：
1. **默认产品不是 4 Agents**：CLI/TUI/Worker 默认 `AgentRuntime` 单工具循环。
2. **MetaGPT 是可选切片**：`packages/agent_core` 有轻量 Role/Team，Worker 仅当 `engine=metagpt` 时调用 `run_metagpt_team`；事件契约和工具权限尽量与 LangGraph 对齐，但不是默认路径。
3. **扩展模型是 PluginHost**：`load_plugin_tree` 组装 tools / commands / hooks / skills / MCP。内置插件提供默认工具与斜杠命令；**未信任工作区跳过** `.zhixiao/plugins`。CLI、TUI、Worker 共用这棵树。
4. **Plan**：默认图里是计划节点 + LangGraph interrupt；Workflow DSL 才按角色节点编排。不要把 GOAL 文档里的 4 个内容 Agent 说成当前实现。

**追问**：MetaGPT 发版要不要跟进？
**应答**：只跟模式（Role/Team/工具权限），不绑框架包版本；默认路径继续走 LangGraph + PluginHost。

## Q10. 工具从哪里来？如何防止越权？

**参考答案**：
1. **不是全局单例 `@register_tool` 扫全库**：默认工具由内置插件 `core.tools` 经 `PluginContext.register_tool` 挂到本次 `PluginHost.tools`（`ToolRegistry` 是 host 上的实例，按工作区/信任度组装）。
2. **消费方只读组装结果**：Runtime / slash / TUI / Worker 的 `assemble_job_registry` 都走 `load_plugin_tree`，不直接 import 各个 Provider。
3. **权限**：`read_only | edit | execute | full`；危险命令、联网、MCP、Git 发布还要 ops/network capability + 审批。`--yes` 只批计划，不批 `git push`。
4. **`CommandPolicy`**：无审批拒绝 `git push` / `rm -rf` 等；工具路径必须落在 workspace 根内（`WorkspaceBoundary`）。
5. **模式收紧工具表**：`--mode ask|plan|review` 只广告只读工具；行为门禁 `ask-read-only` 覆盖「EDIT 权限 + ask 模式仍不能 write」。

**追问**：你们怎么防 LLM 误用工具？
**应答**：1) 只把当前 run 允许的 schema 传给模型；2) 执行前再做权限/策略/workspace 校验，失败返回 `blocked` 而不是默默跑；3) 事件里留下 tool_result，Web 证据条展示 permission / verification / termination，缺字段显示「未回报」。

## 通用应答思路

回顾项目时使用 STAR 模型：
- **S**ituation：要把模型接到真实仓库，风险是越权、中断不可恢复、把未验证当成成功。
- **T**ask：交付可审计的软件工程 harness（权限 × worktree × 验证 × 插件组装），而不是 4-Agent 内容平台，也不是已交付的 LoRA/百万召回控制台。
- **A**ction：LangGraph + SQLite interrupt/resume、PluginHost、CommandPolicy、FastAPI/Worker/Vue SSE 与运行证据条、离线行为门禁。
- **R**esult：只展示 GitHub Actions 与 `tests/evals` 制品。没有 live 评测文件时明确说尚未实测；**不要**引用 fixture 上的 task_completion_rate / hallucination_rate。

度量自驱：量化指标必须能定位到固定评测结果或 CI 制品；没有证据时只讨论目标，不宣称达成。
